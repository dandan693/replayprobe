# replayprobe 项目方案

> 这份文档回答七个问题：**为什么成立、为什么必须做、谁会用、
> 数据从哪来、怎么评、拿什么指标说话、每个技术选择为什么是它。**
>
> 所有数字都是本仓库实跑出来的，命令附在对应位置，可以逐条复核。
> 凡是没验证过的、做不到的，写在最后一节「已知局限」里，不在这里充数。

---

## 一、合理性：这个项目为什么成立

### 1.1 问题的真实形态

Agent 一旦上线，就会被反复改动：换模型、改提示词、升工具版本、调温度、加一条系统约束。
每次改完都要回答一个问题：**这次改动有没有把行为改坏？**

现有的两种回答方式都不回答这个问题：

| 现有做法 | 它回答什么 | 它漏掉什么 |
|---|---|---|
| 重跑一遍看日志 | 这一条看起来对不对 | 人只能看几条；"路走歪了但结论对了"完全看不出来 |
| 跑评测集看分数 | 准确率涨了还是跌了 | 分数不变时，行为可能已经面目全非 |

**"分数没掉但路走歪了"是真实存在的一类问题**，而且是最贵的一类：
它还留在绿灯里，直到某天因为成本、延迟或边界条件突然翻车。

### 1.2 项目成立的关键：把"回放"当成一等公民

要判断"路是不是同一条"，前提是**能把一条已经跑过的轨迹原样重跑一遍**。

这件事在 Agent 领域一直很难，因为它有三个非确定性来源：
模型输出、外部工具、时间/并发顺序。但仔细看会发现：

- **工具是确定性的**（只要它是纯函数式的 DB 查询 / 计算）—— 可以被造出来。
- **时间/并发顺序**可以不用 —— 只要用单调 `seq` 而不是时间戳排序。
- **只剩模型输出这一个真正的非确定性来源**，而它恰好是最适合"录下来"的：
  模型调用是**离散、可枚举、有明确输入输出**的。

三个来源收敛成一个，这个项目就成立了：**录下模型在每个决策接缝上的输入输出，
其余全部做到确定性，于是"重跑一遍"变成一个可实现的工程问题。**

### 1.3 一个前提条件：判据本身必须可复现

这是本项目最关键的一步推理。

要判断"两条轨迹是不是同一条路"，需要某种判据。最容易想到的判据是
**再叫一个模型来判**（"这两步是不是一个意思？"）。这条路必须堵死 ——

> **用不可复现的判据，去测可复现性，是自相矛盾的。**

因为判据本身会漂，你就永远分不清"这次分叉是真的"还是"裁判今天心情不同"。

所以全项目的判据只用三种确定性手段：**字符串规范化、内容哈希、集合运算**。
唯一的例外是"两侧都没有结论数字时的文本相似度"，
它被显式暴露成可调参数并在每条证据里回显 —— **可调的东西必须看得见。**

## 二、必要性：不做会怎样

### 2.1 不做的话，你会花在错的地方

改一次提示词后看到"12 条任务出现分叉"，人的第一反应是去改那 12 条。
但如果**分叉其实是假的**（整体错位造成的错觉），你就是在改没坏的地方。

本项目用对照实验量化了这个假象：

```bash
python tools/demo_replay.py    # 第 ③b 段
```

```
序号对齐（朴素做法）报出 2 处决策分叉
签名对齐（本项目）  报出 0 处决策分叉

真实情况：只有 1 处新决策，其余"分叉"全是多了一步之后整体错位造成的假象。
```

**这个错误方向特别恶劣：它看起来像真的发现了问题** ——
报告里长长一串分叉，没人会怀疑是工具算错了。

### 2.2 不做的话，门禁会因为太吵而死

如果所有差异都记成"分叉"，那么温度不为零时措辞每天都在变，
门禁天天红。两周内团队就学会在 CI 里加 `--skip`，然后它彻底没用。

**这就是五档量表存在的理由。** D1（措辞变了）本来就该放行，
D3/D4 才该拦。把 D1 和 D3 记成同一件事，是这类门禁最常见的死法。

### 2.3 不做的话，观测工具永远停在调试阶段

Langfuse / Phoenix / LangSmith 都能让你**看见**差异。但它们不回答
"这个差异可不可接受" —— 因为那需要一条**策略**，而不是一个视图。

流水线需要的是一个**能返回退出码的判断**。本项目补的就是这一环：
把策略写成 JSON，让 CI 去判。

## 三、场景：谁在什么情况下用它

### 场景 A：改提示词（最常用）

> "我在系统提示里加了'不要编造数字'，会不会让模型变得更啰嗦、多绕几步？"

配置 `data/budgets/prompt_tweak.json`：前 2 步（选工具、取数）必须完全稳定，
之后允许最多 30% 的任务出现路径分叉。用 `drill --fork-at 2` 做反事实对照。

**它把"这次改动的影响范围"从形容词变成了一个数字。**

### 场景 B：换模型

> "把 gpt 换成便宜一半的 qwen，答得还是不是同一件事？"

配置 `model_swap.json`：**路径允许大改**（不同模型的习惯本来就不同），
但**结论不许变**，且绝不能出现安全分叉。
这是"省下的钱值不值得"这个问题的可执行版本。

### 场景 C：定位一个偶发 bug

> "偶发：十次里有一次它会忘了加 DISTINCT，把行数当客户数。"

`drill` 模式的问题恰恰相反 —— 你需要的是**大量重放同一个带**，
看有没有一次走出不同的路（`exact` 模式跑 N 次；理论上应当 100% 一致，
一旦某次不一致，那就是模型侧或工具侧有隐藏的非确定性，
**这个"不一致"本身就是最有价值的发现**）。

### 场景 D：当 CI 门禁

在合并前跑一遍，退出码非 0 就拦下，并把违例逐条打出来。

## 四、数据集构建：这里的"数据"是什么

这个项目的数据集有两层，**必须分开说**，否则会被追问"你这算不算造数据"。

### 4.1 领域数据集：真值库（可验证、可复现）

复用同作者 `evalguard` / `faultprobe` 的领域数据：UCI Online Retail 清洗后
**392,692 行**。构建脚本 `tools/build_truth_db.py --download` **自己把原始数据取回来**
（UCI 现在只给 xlsx，零依赖解析，见 `replayprobe/dataset.py`），再三步清洗：

| 步骤 | 操作 | 剩余行数 |
|---|---|---|
| 0 | 原始 | 541,909 |
| 1 | 去重 | −5,268 |
| 2 | 删客户号缺失 | −135,037 |
| 3 | 删非正数量 / 非正单价 | −8,912 |
| — | **最终** | **392,692**（保留率 72.5%） |

**换了一条取数通路，就必须证明结论没变。** 实测做法：拿本机那份老的
ISO-8859-1 CSV，和新脚本从 xlsx 转出来的 CSV **各建一次库、逐行比对** ——
392,692 行**逐行完全一致，0 处差异**。所以「下载到的数据是不是同一份」
这个问题不是靠相信，是靠比对回答的。

关键指标全部来自真值库实跑，**没有一个数字是编的**（`llm.py` 的 `TASKS` 里
每个任务的 `answer` 都对应一条真实 SQL）：

| 指标 | 值 | 用在哪 |
|---|---|---|
| 全量总销售额 | 8,887,208.89 | `total` 任务的基线结论 |
| 英国总销售额 | 7,285,024.64 | `total` 的 `wrong_sql`（口径错位） |
| 订单数 | 18,532 | `orders` 任务；`total` 的伴随数字 |
| 客户数 | 4,338 | `customers` 任务 |
| 订单数 vs 行数 | 18,532 vs 392,692 | `orders` 的 `wrong_sql`：把行数当订单数 |

`wrong_sql` / `wrong_answer` 不是随便写的错，它们对应**两类真实高频的口径错误**：
把行数当订单数、忘了 `DISTINCT`。这样演示里的"结论分叉"才是可信的，
而不是一个没人会犯的假想错误。

### 4.2 轨迹数据集：录制带（这是本项目的真正产物）

**"数据集"在本项目里主要指的是录制带**，它由真实运行产生：

```bash
python -m replayprobe run --task total --variant baseline --out reports/base.json
#   录制带 reports/base.tape.json（3 条记录）
#   轨迹   reports/base.json（4 步）
```

一份带的内容：

```
TapeManifest   身份 + 不可变指纹
               tape_id / task_id / agent_variant / model / model_revision /
               prompt_hash / tool_schema_hash / dataset_snapshot / limitations
TapeEntry      每个决策接缝一条
               seq（单调序号，不是时间戳）/ kind / key（输入指纹）/
               payload（输出原文）/ input_hash / output_hash / parent_seq / meta
```

**数据集的真实性由三条设计保证：**

1. **带里只放客观发生了的事。** 不放任何"我认为它想干什么"的推断 ——
   推断错了就永远查不出来，因为带会说"当初就是这么决策的"。
2. **身份用不可变指纹，不用版本名。** `model=gpt-x, prompt=repair-v4` 是弱证据：
   别名可能指向不同权重，prompt 可能被就地改过。
3. **做不到的如实写进 `limitations`。** 例如"只记录了模型别名，
   未记录具体服务版本 —— 别名可能指向不同权重"。这是诚实与自我欺骗的分界线。

**数据集的可获得性**：开箱可见 —— `tools/build_truth_db.py --download` 自己取数
（唯一需要联网的一步，之后全程离线），再加三个脚本化变体
（`baseline` / `late_fork` / `scope_confusion`），**不需要 API Key**
就能产出一整套可比较的轨迹。这是刻意的：

> 一个需要联网才能跑的框架，没人会在 CI 里跑它；而没人跑的门禁，等于不存在。

## 五、评测设计：怎么评

### 5.1 被评对象与评测方式

**被评对象**：一次「改动前 vs 改动后」的行为差异。

**评测方式**：不是"打分"，是**分级 + 结算**。三步：

```
① 录制          真实跑一遍 → 带（记录每个接缝的输入输出）
② 回放/钻取     用带重放，或从指定步开始真实执行 → 新轨迹
③ 对齐 + 分级   签名序列对齐 → 定位第一处分叉 → 落到 D0~D4
④ 预算结算      按 JSON 策略判是否放行 → 退出码
```

### 5.2 分级判据（全部确定性，零模型调用）

| 判据 | 手段 | 输出 |
|---|---|---|
| 决策是否相同 | 规范化 payload 的内容哈希 | 签名相等 / 不等 |
| 结论是否被推翻 | 结论数字的**集合运算** | `same` / `b_superset` / `a_superset` / `differs` / `both_empty` |
| 是否只是措辞 | `full` 级签名有差、`decision` 级签名无差 | D0 vs D1 |
| 是重试还是新探索 | 插入步的决策签名是否已在基线签名集合中出现过 | D1 vs D2 |
| 是否拒答 | 拒答标记词表 | D4 触发条件之一 |
| 是否崩溃 | 完整步列表里有没有 ERROR 步 | D4 触发条件之一 |
| 两侧都无数字时的文本差异 | `difflib.SequenceMatcher` 比率 | 唯一的模糊判据，阈值可配且回显 |

**两个"用结构运算替代语义判断"的地方**，是这套设计里最经得起追问的部分：

**① 数字集合关系**
```
{8887208.89}  vs  {8887208.89, 18532}   → b_superset → 信息量变了，不是推翻 → D2
{8887208.89}  vs  {4443606.45}          → differs    → 原数没了，被替换     → D3
```
为什么多答一个数不算推翻结论？**因为原结论的每一个数字都还在，
它没有被任何新证据否定。** 这个理由不依赖任何模型判断。

**② 重试 vs 新探索**
插入步的决策签名如果已经在基线里出现过 → 是重试（D1）；
出现了一个基线里从没有过的工具调用 → 是新探索（D2）。
不做这个区分，改一次提示词后模型偶然多试一次 SQL 就会淹没在 D2 里。

### 5.3 评测自身的可信度（怎么证明裁判没坏）

这是最关键的一节 —— **一个判错的裁判比没有裁判更危险**，所以要专门证明裁判是好的：

```bash
python -m replayprobe check        # 五个模块自检全绿
python -m unittest discover -s tests -t .   # 197 项单测
```

| 自证项 | 手段 | 结果 |
|---|---|---|
| 确定性 | 只用一个带重放两次，比对是否 D0 | 逐字一致（D0） |
| 判据可分辨 | 五档各构造一个真实场景，看是否各就各位 | 全部正确落位 |
| 假分叉能被识别 | 序号对齐 vs 签名对齐对照实验 | 误报 2 处 vs 真实 0 处 |
| 不撒谎 | 截断带后看回放反应 | `exact` 抛错 / `strict` 记录偏离，都不编造 |
| 门禁不放水 | 对空集结算 | 判**不通过**（防止 glob 写错就全绿） |

> 最后一条值得单独说：**门禁不能对空集盖章。** 否则 CI 里一个路径打错字，
> 就"全绿"了 —— 而这种全绿看起来和"真的没问题"一模一样。

## 六、指标：拿什么数字说话

### 6.1 主指标

| 指标 | 定义 | 用途 |
|---|---|---|
| **分叉等级 D0~D4** | 单条比较的结论 | 决定拦或不拦 |
| **分叉率** | 达到 `divergence_floor` 的比较数 / 总比较数 | 批次级信号：单条 D2 正常，一半是 D2 就是改动有问题 |
| **匹配率** | 对齐后匹配步数 / 最长侧步数 | 抓"长度差很多但 LCS 仍显示高匹配"的假象 |
| **第一处分叉位置** | 在对齐序列中的下标 | 决定 `allow_fork_after` 是否被击穿 |
| **插入 / 删除步数** | 结构变化的量 | 区分"决策变了"与"形状变了" |
| **未解释的分叉** | 身份全同却出现 D2+ 的次数 | 指向**工具之外**：上游的确定性假设出了裂缝 |
| **改动变量** | `changed` 列表 | 回答"这次比较到底改了什么"，也是 `--select` 的筛选键 |

`divergence_floor` 是后来补的一个**计数口径**。第一版把"分叉率"写死成
"D2 及以上"，于是它和 `max_severity` 会互相打架：`model_swap` 声明
"路径允许大改"（上限 D3），却又用 D2 计入的比率把 100% 的 D2 判成违规 ——
**这份预算永远无法通过，而它恰恰是"换便宜模型值不值得"唯一的可执行表达。**

拆开之后，`max_severity` 管"最坏那条能坏到什么程度"，
`divergence_floor` 管"从哪一档起算它被碰到了"。`Budget.audit()`
会拦下 `floor` 低于 `max_severity` 的配置：被明确允许的等级，
不该又被算进违规率。

### 6.2 实测结果（本仓库真实跑出来的）

**五档分级全部正确落位：**

| 场景 | 期望 | 实测 |
|---|---|---|
| 两次 exact 互比 | D0 | D0 ✓ |
| baseline vs exact | D0 | D0 ✓ |
| 仅措辞变化 | D1 | D1 ✓ |
| 多答一个数（原数都在） | D2 | D2 ✓ |
| 换了查询条件但结论一致 | D2 | D2 ✓ |
| 多试一次同样的 SQL（重试） | D1 | D1 ✓ |
| 多查一次表结构（新探索） | D2 | D2 ✓ |
| 金额被替换 | D3 | D3 ✓ |
| 占比 74.66% → 74.65% | D3 | D3 ✓ |
| **8887208.894 → 8887208.89（仅精度）** | **D2 起（不当 D3）** | 不判 D3 ✓ |
| 变成拒答 | D4 | D4 ✓ |
| 正常 vs 崩溃 | D4 | D4 ✓ |

**端到端链路：**

| 步骤 | 结果 |
|---|---|
| `python -m replayprobe check` | 5 个模块自检全绿；真值库 392,692 行 |
| 录制 `total / baseline`（脚本替身） | 带 3 条记录，轨迹 4 步 |
| `exact` 重放 | 4 步，用带 3 步 / 真实执行 **0** 步 |

| `gate --budget default` | 未通过，退出码 **1** |
| `gate --budget model_swap` | 通过，退出码 **0** |
| `tools/demo_replay.py` | 五段全通过，退出码 **0** |
| 单测 | **197 项全绿**（2.6s，零依赖；其中约 2s 来自一条真的起 socket 的卡死复现测试） |

**真实模型实测（2026-09-25，`qwen-plus-latest` / `qwen-turbo`）：**

| 实验 | 自变量 | 组数 | 结果 |
|---|---|---|---|
| 对照组 | 什么都没改 | 5 | 全部 **D0** |
| 温度 | 0 → 1.0 | 1 | **D0**（六条轨迹 steps 哈希相同） |
| 提示词 | 追加一条规则 | 1 | **D2**（插入 2 步，结论不变） |
| 模型 | plus → turbo | 2 | **D2**（写法变了，结论不变） |

### 6.3 这次实测修掉了两个误报

这两条值得单独写，因为**它们都属于"判据出错"而不是"框架出错"** ——
框架的 bug 会报错，判据的误报只会安静地给你一个错结论。

**(a) 精度差异被判成结论被替换（D3）。**
真实模型答 `8887208.894`，脚本替身答 `8,887,208.89`，同一次 `SUM` 的两种表述，
第一版判 D3 —— 而 D3 是"该拦下来"那一档，误报代价最高。
改用"短数是不是长数的四舍五入"这条确定性判据（`same_number`）。
**不用相对误差阈值**：在 8887208 这个量级上"相对误差 < 1e-6"等于允许 ±8.89 偏差，
会把 8887200 和 8887208 也判成同一个数。

**(b)「什么都没改却分叉」的告警在 drill 比较上误报。**
drill 的分叉是工具自己故意切出来的，拿它报"上游非确定性"等于把实验设计当故障。
判据收紧为：**只有两侧都是 `live` 的独立重跑才有资格报这条。**

顺带发现第三个小问题：drill 比较一度被归进「什么都没改」组，
把对照组的 0% 分叉污染成 14.3% —— 根因是 `changed` 里漏了
**运行方式（mode）** 这个自变量。**拿两个东西来比，它们的全部差异就是自变量；
漏掉一个，对照组就不纯了。**

## 七、技术选型理由

### 7.1 为什么零第三方依赖

**理由不是洁癖，是准入成本。** 门禁的价值来自"别人真的会跑它"。
每多一个依赖，愿意在一个陌生仓库里跑它的人就少一截。
所以全部只用标准库：

| 需要的能力 | 选型 | 为什么不用常见的那个 |
|---|---|---|
| 序列对齐 | `difflib.SequenceMatcher` | 不需要 `python-Levenshtein` / `biopython`：本条轨迹最长几十步，`difflib` 的性能完全够 |
| 数据存储 | `sqlite3` | 不需要起 Postgres / DuckDB：单机只读真值库，标准库自带且支持 `mode=ro` |
| HTTP（仅录制真实轨迹时需要） | `urllib.request` | 不需要 `openai` SDK / `requests`：本项目只需要"发一条 chat 请求拿一条回复"，不是要做 SDK |
| 报告 | 手写 HTML/SVG | 不需要模板引擎 / 图表库：**一个报告生成器如果需要联网才能渲染，那它在演示现场就会挂** |
| 测试 | `unittest` | 不需要 pytest：标准库能跑，装了 pytest 也能跑（两者兼容），但反过来不成立 |

### 7.2 为什么对齐用签名而不是序号

见第二节的对照实验。核心一句：**改提示词最常见的后果是"多做了一次"，
而不是"做错了"**，多一次之后所有序号整体错位。

朴素实现 `align_by_index` **被刻意保留**在 `align.py` 里 ——
它不是"没删掉的旧代码"，而是对照实验的另一组。删掉它，README 里那个
"误报 2 处 vs 真实 0 处"的数字就没有出处了。

### 7.3 为什么规范化只做表面、不做语义

- **太强** → 把真分叉抹平。`SELECT SUM(amount)` 和 `SELECT SUM(qty)`
  如果都被抹成"一个 sum 查询"，那就漏报了。
- **太弱** → 稳定存在的空格差异被记成路径分叉，同样是噪音。

**取舍：只做空白 / 大小写 / 标点 / 末尾分号，不做等价重写。**
理由是**可解释性**：表面规范化能说出"改了哪几个字符"，
而语义规范化要么引入 SQL 解析器（重），要么引入模型判断（不可复现）。

代价是：等价的 SQL 改写会被判成分叉（误报）。
**这是"宁可误报，不引入不可复现判据"的刻意选择**，已写进已知局限。

### 7.4 为什么回放要分三种模式

因为它们是**三个不同的实验**，混为一谈是调试 Agent 时最容易骗到自己的地方：

- `exact` 回答"这条轨迹本身完好、且可复现吗"（可复现性自证）
- `strict` 回答"新版本从第几步开始走岔了"（回归检测）
- `drill` 回答"如果第 N+1 步换个做法，后面会怎样"（反事实实验，控制变量法）

「重放一次看起来一样」**不等于**「行为被复现了」——
所以模式必须显式选、报告里必须回显。

### 7.5 为什么 `seq` 而不是时间戳

并行工具完成的顺序可能和发起的顺序不同。**按时间戳排序会得到一份
"看起来对"的轨迹** —— 这种错最难查，因为它不报错，只是把因果讲反了。
所以用单调 `seq` + 指向因果父节点的 `parent_seq`。

### 7.6 为什么 `model` / `usage` 不进内容签名

第一版把它们塞进了 `payload`，自检立刻报错：`late_fork` 与 `baseline`
的第 1 步明明都是同一次调用，却因为 `model` 字段一个是 `scripted-baseline`、
一个是 `scripted-late_fork` 而被判成不同。

这在真实场景里是个坑：模型名常带日期后缀（`qwen-plus-2026-09-25`），
升个版本号就会让所有 `full_signature` 失效，于是**满屏 D1**，
而行为其实一模一样。**元信息不该参与内容比较。**

### 7.7 为什么保留"失败路径的权威 payload"

工具失败时，录制层把权威 payload 通过 `setattr(exc, "replayprobe_payload", payload)`
挂在异常上，agent 层优先用它，**不在 agent 那边重建一份**。

因为"两处各自构造同一份数据"是最容易悄悄漂移的写法：
录制层记成 `TypeError: xxx`，agent 可能重建成 `RuntimeError: xxx`，
于是重放时这一条对不上，**凭空多出一处假分叉**。
失败路径的一致性必须和成功路径一样有保证。

### 7.8 为什么真实模型走原生 function calling，还留着标签协议

两条路都实现，不是"兼容性更好"这种空话，是因为**协议不匹配的失败是静默的**：

模型明明调了工具，而我们只看到一段纯文本，于是要么把这次调用当成
"任务完成"记进轨迹，要么整条轨迹失去意义 —— **两种都不报错**。

所以：请求里带 `tools`（原生），同时从 `content` 里找
`<tool_call>{...}</tool_call>`（兜底）；两条都走不通时**明确报错**。
赌一条比走两条要危险得多。

配套的两条纪律：

- **不能解析时必须抛错，不能猜。** 参数不是合法 JSON、`<tool_call>` 标签未闭合，
  一律报错。猜一个"看起来合理"的参数塞回去，会在轨迹里记下一次
  **根本没发生过的**工具调用 —— 这比崩溃难查得多。
- **`finish_reason` 只进 meta。** 同一个语义在不同供应商那里取值不同
  （`tool_calls` / `stop`），塞进 payload 会让"同一件事"因供应商不同而签名不同，
  又是一批假分叉。但它必须被记下来：`length` 意味着响应被截断，
  这样的轨迹该被筛掉，而不是混进统计污染结论。

接之前先用 `tools/probe_real_llm.py` 跑一次裸调用把原始返回打出来，
成本可以忽略，但能一眼看清协议对不对 —— 比在完整链路里归因便宜得多。

## 八、已知局限（不做包装）

### 判据

1. **只覆盖决策接缝**（LLM 调用与工具调用）。多进程 / 异步并行下的真实因果还原
   只预留了 `parent_seq` 字段，未实现。
2. **文本相似度是全项目唯一的模糊判据**，只在"两侧都没有显著结论数字"时启用，
   默认阈值 0.85 是取舍不是真理。
3. **年份会被误收为结论数字**（整数且 ≥ 100）。误报在实践中很少触发，但真实存在。
4. **不做 SQL 语义等价重写** —— 等价改写会被判成分叉（见 7.3 的取舍）。
   （**数字**层面的精度差异已被容错，见 6.3；这与 **SQL 文本**层面的等价重写不是一回事。）
5. **`intent` 级未接入分级主链路**，只是可用的第三种分辨率。
6. **不做内容寻址去重**：`input_hash` 已经存下来了，但同一个 prompt
   重复出现时仍会存多份。
7. **不处理多模态与流式输出。**
8. **`same_number` 只处理"小数位数不同"**，不处理"换了口径算出的近似值" ——
   那本来也不该被容忍。
9. **`unexplained_fork` 只报异常、不定位。** 它分不清是供应商路由、缓存还是权重漂移。

### 接入

10. **模型别名不是身份。** `model_revision` 为空，别名指向的权重可能变。
    真实模型的结论应读作"某一天的实测"，而不是"该模型的固有性质"。
11. **`temperature=0` 不等于确定性，本项目不这么承诺。**
    实测中温度 0 与 1.0 都没分叉，但那是**这条任务**的性质。
12. **只支持 OpenAI 兼容协议 + 一种标签兜底**，别的供应商要另接。
13. **不支持多工具并行调用**：一次返回多个 `tool_calls` 时只执行第一个，
    但会把总数记进 meta，不让它无声无息过去。
14. **不做成本核算**：`usage` 存在 meta 里，没有汇总成钱。

### 数据

15. **真值库不进仓库**（约 69 MB），需本地跑 `tools/build_truth_db.py --download` 生成。
16. **原始数据也不进仓库**（24 MB zip + 48 MB CSV），由 `--download` 自动取回并缓存。
17. **录制带默认不进仓库**（含完整模型输入输出）。
    唯一的例外是那条 `qwen-plus-latest` 的样本 —— 刻意入库，
    让"重放"这件事可以被任何人离线验证。要放行自己录的带当 CI 基准，先脱敏。
18. **下载不支持断点续传 —— 是服务器不支持，不是没做。** 实测 `Range` 头被 UCI
    忽略（无 `Accept-Ranges`，带 Range 的请求仍返回整个文件），所以重试只能从头再来。
    现在有两条独立通路（zip → xlsx 直链）+ 3 次退避重试 + `.part` 完整性校验
    + 每次尝试都打日志。实测记录见 `docs/真实实验记录.md` 8.5 / 8.6。
19. **单步超时 120 秒，且它是"每一步"的超时、不是总时长。**
    实测撞见"连接被接住但不回数据"会静默枯等满整个超时 ——
    600 秒 × 3 次重试就是半小时零输出，所以收敛到 120 秒并暴露成
    `--download-timeout`。慢链路可以调大。
