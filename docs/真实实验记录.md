# 真实模型实验记录

**日期**：2026-09-25
**模型**：阿里云百炼 `qwen-plus-latest`、`qwen-turbo`（OpenAI 兼容端点，原生 function calling）
**数据**：`retail_truth.db`（392,692 行，UCI Online Retail 清洗后）
**代码版本**：本仓库当前 HEAD
**目的**：把脚本替身的结论放到真实模型上验一遍 —— 并如实记录**与预期不符**的部分。

## 0. 为什么必须先做一次裸调用

接真实模型时最常见的失败不是"连不上"，而是**连上了但协议对不上**：
模型把工具调用写成了纯文本、响应被 `finish_reason=length` 截断、
或者干脆不用工具直接编了个数字。

这些在完整链路里只会表现为"轨迹有点怪"，很难归因。所以先跑一次
`tools/probe_real_llm.py`，把**原始返回**打出来：

```
$ python tools/probe_real_llm.py --api-key-file <key> --model qwen-plus-latest
模型    qwen-plus-latest  temperature=0.0
工具 schema（3 个）：calc(expression) / get_schema(table) / run_sql(sql)
问题    全量总销售额是多少美元？
原始返回体检：
  model         'qwen-plus-latest'
  finish        'tool_use'
  finish_reason 'tool_calls'   （供应商原始值，只进 meta 不进签名）
  content       0 字
  tool_call     {"name": "run_sql", "arguments": {"sql": "SELECT SUM(Amount) AS total_sales FROM retail"}}
  usage         {"completion_tokens": 28, "prompt_tokens": 513, "total_tokens": 541}
[ok] 工具 run_sql 实跑成功：[{"total_sales": 8887208.894}]
探针结论：协议可用，可以录真实轨迹了。
```

两点值得记下来：

1. **原生 function calling 模式下 `content` 是空的。** 内容全在 `tool_calls` 里。
   如果只解析 content，会把这次调用误判成"模型没调工具"→ 进而记成"任务完成"。
2. 模型自己选了 `SELECT SUM(Amount)` 这一条 SQL，**和我们没给它任何 schema 提示
   也没关系**（`SCHEMA_HINT` 只在工具描述里）；它实跑出来的
   `8887208.894` 与真值库一致。

顺带记录一次环境事实：`qwen-plus` 这个**别名**的免费额度已用尽
（`HTTP 403 AllocationQuota.FreeTierOnly`），而 `qwen-plus-latest`、`qwen-turbo`、
`qwen-max`、`qwen-flash`、`qwen-long`、`qwen3-max` 可用。
**同一个家族里别名与 -latest 是两个不同的配额桶** —— 这正是"别名不算身份"的活例子。

## 1. 实验设计

四组实验，每组只改一个变量：

| 实验 | 自变量 | 组数 | 期望 |
|---|---|---|---|
| ① 对照组 | **什么都不改**（同模型、同 prompt、同温度） | 5 | D0 |
| ② 温度 | `temperature` 从 0 → 1.0 | 1 | ？ |
| ③ 提示词 | system prompt 追加一条规则 | 1 | D2+ |
| ④ 模型 | `qwen-plus-latest` → `qwen-turbo` | 2 | D2 或 D3 |

录制命令（以对照组为例）：

```bash
P=python
K=/path/to/key.txt
for i in 1 2 3; do
  $P -m replayprobe run --task total --llm real --model qwen-plus-latest \
     --temperature 0 --api-key-file "$K" --out "reports/t0_$i.json"
done
```

第 ③ 组用的追加规则是：

```
4. 给出结论前，必须先调用 get_schema 确认表结构。
```

## 2. 轨迹内容（逐条可复核）

### ① 对照组 · `t0_1 / t0_2 / t0_3`（温度 0）与 `t1_1 / t1_2 / t1_3`（温度 1.0）

**六条轨迹的 `steps` 规范化哈希完全相同**：`c573fc3290f7a757fe725614`

```
seq1 LLM   → 工具调用 run_sql  {"sql": "SELECT SUM(Amount) AS total_sales FROM retail"}
seq2 工具  → [{"total_sales": 8887208.894}]
seq3 LLM   → 直接作答：'全量总销售额是 8887208.894 美元。'
seq4 FINAL → '全量总销售额是 8887208.894 美元。'
```

文件哈希不同（`t0_1.json` = `e7e18610…`，`t1_1.json` = `b5565756…`），
因为 `variant` 标签里带了温度（`real:qwen-plus-latest@t0.0` vs `@t1.0`）。
**行为一致，标签不同** —— 这正是"元信息不参与内容比较"的价值所在。

另一条对照组（换到有口径陷阱的任务 `customers`）：

```
plus_cust_1 / plus_cust_2   steps 哈希 cd3abdafd1c3c64875efc5f8（两条相同）
seq1 LLM   → 工具调用 run_sql  {"sql": "SELECT COUNT(DISTINCT CustomerID) AS customer_count FROM retail"}
seq2 工具  → [{"customer_count": 4338}]
seq3 LLM   → '一共有 4338 位客户。'
seq4 FINAL → '一共有 4338 位客户。'
```

模型**没有**掉进 `COUNT(*)` 的陷阱，两次都写了 `DISTINCT`。

### ② 温度 1.0

即 `t1_1 / t1_2 / t1_3` —— 已包含在上面那一组里，因为**它们和温度 0 完全一样**。

### ③ 改提示词 · `prompt_plus`

```
文件哈希 2cf636fb…   5 条录制记录 / 6 步（对照组是 3 条 / 4 步）
prompt_hash a234d49997639662 → bf5722c6d1f98b54

seq1 LLM   → 工具调用 get_schema  {}          ← 新提示词要求的
seq2 工具  → [10 个列名]
seq3 LLM   → 工具调用 run_sql  {"sql": "SELECT SUM(Amount) FROM retail"}
seq4 工具  → [{"SUM(Amount)": 8887208.894}]
seq5 LLM   → '全量总销售额是 8887208.894 美元。'
seq6 FINAL → '全量总销售额是 8887208.894 美元。'
```

**结论没变（数字一模一样），但第一步的工具选择变了。** 判定 D2，
对齐结果是「插入 2 步」（`get_schema` 及其返回）。

### ④ 换模型 · `turbo_total` / `turbo_cust`

```
turbo_total（task=total）
seq1 LLM   → 工具调用 run_sql  {"sql": "SELECT SUM(Amount) FROM retail;"}   ← 无别名，带分号
seq2 工具  → [{"SUM(Amount)": 8887208.894}]
seq3 LLM   → '全量总销售额是 8887208.894 美元。'                          ← 与 plus 逐字相同

turbo_cust（task=customers）
seq1 LLM   → 工具调用 run_sql  {"sql": "SELECT COUNT(DISTINCT CustomerID) FROM retail;"}
seq2 工具  → [{"COUNT(DISTINCT CustomerID)": 4338}]
seq3 LLM   → '一共有4338位客户。'                                        ← plus 是「一共有 4338 位客户。」（带空格）
```

`qwen-turbo` 更便宜，**结论一次都没错**，但 SQL 写法和措辞习惯都和 plus 不同。

## 5. 四个结论

### ① temperature=1.0 没有产生任何可观测分叉

这是最反直觉的一条。3 次温度 0 + 3 次温度 1.0，六条轨迹的 `steps` 哈希相同。

> **分叉的来源不是温度，是任务有没有选择空间。**

"算一下全量总销售额"这个任务只有一条合理的路：调 `run_sql`、拿数、给结论。
采样温度再高也没有别的选项。

**推论（比结论本身更重要）**：如果拿这个任务去论证"我们的 Agent 很稳定"，
结论是不可信的 —— **一个没有选择空间的任务，测不出稳定性**。
要测稳定性，得用有多个可行路径的任务（比如"给出门店经营诊断"，或 `customers`
这类存在 `COUNT(*)` / `COUNT(DISTINCT)` 两种读法的陷阱任务）。

### ② 真正制造分叉的是"改一个变量"

- 追加一条 prompt 规则 → 第一步立刻变了，且被正确识别为**插入 2 步**，
  而不是"后续整体错位"。这正是签名对齐相对于序号对齐的价值。
- 换成 `qwen-turbo` → SQL 写法与措辞变了，**结论数字一字未变** → D2。

### ③ 两个"该准的地方"被真实模型撞出了误报，都已修

**(a) 精度差异被误判成结论被替换（D3）。**

真实模型答 `8887208.894`（SUM 的原始值），脚本替身答 `8,887,208.89`（保留两位）。
第一版判「数字集合被替换」→ D3。

**D3 是"该拦下来"的那一档，它的误报代价最高** ——
模型只要改个小数位数，门禁就会红；这种红法持续两周，团队就会加 `--skip`。

修法是用**确定性且可解释**的判据替代集合相等：
短的那个数是不是长的那个数四舍五入到它自己的小数位数。
不用相对误差阈值 —— 在 8887208 这个量级上，"相对误差 < 1e-6" 等于允许 ±8.89 的偏差，
那会把 8887200 和 8887208 也判成同一个数。

（同时确认：一侧一个显著数字都没有、另一侧有 → 仍然判 `differs`。
这种放宽不能顺手做，会静默削弱 D3 档。）

**(b)「什么都没改却分叉」的告警在 drill 比较上误报。**

这个告警的本意是回答："我看到的分叉，是我改出来的，还是上游本来就有的？"
第一版只检查"变量没改"，结果在 `drill` 比较上触发了 ——
而 drill 的分叉是**工具自己故意切出来的**（前 N 步用带，之后走真实执行）。

拿它去报"上游不稳定"，等于把实验设计当成了故障。判据已收紧为：
**只有「两侧都是 live 的独立重跑」才有资格报这条。**

顺带一个小发现：drill 比较一度被归进「什么都没改」那一组，
把对照组的"0% 分叉"污染成了 14.3%。根因是 `changed` 里没有把
**运行方式（mode）**算作自变量。已补 —— 我拿两个东西来比，
它们之间的**全部**差异就是这次实验的自变量，漏掉一个，对照组就不纯了。

### ④ 对照组 5 条全 D0，本身就是有价值的结论

它说明在这条任务上、在这一天、这个端点、这个模型别名下，**上游是稳定的**。
将来 `unexplained_fork` 一旦触发，你就知道该去找供应商，而不是翻自己的 diff。

**没触发也是数据。** 只报"发现了问题"的实验记录是不完整的。

## 6. 一件事：这条真实轨迹可以被离线重放

对照组的一条真实轨迹已作为样本入库：

```
data/tapes/real_qwen-plus-latest_t0_total.tape.json
data/tapes/real_qwen-plus-latest_t0_total.trace.json
```

**不装任何依赖、不要 API Key、不联网**，就能把它逐字重放出来：

```bash
python -m replayprobe run \
  --tape data/tapes/real_qwen-plus-latest_t0_total.tape.json \
  --mode exact --out reports/real_exact.json
#   模式 exact | 4 步 | 用带 3 步 / 真实执行 0 步

python -m replayprobe compare \
  --a data/tapes/real_qwen-plus-latest_t0_total.trace.json \
  --b reports/real_exact.json
#   分叉判定：d0_identical
```

**为什么文件哈希不同却判 D0**：重放出来的步带 `source: "tape"` 和 `tape_seq`，
录制的步是 `source: "live"`。这两个字段是**来源标注**，不是行为 ——
签名比的是 `payload`，所以判定 D0 是对的。
（这也解释了为什么 `real_exact.json` 的 steps 哈希 `eaea8f14…` 与原始轨迹
`c573fc32…` 不同：内容相同，标注不同。**判据只看行为，不看来源。**）

已核查：这两个文件不含 API Key、不含凭据、不含 Authorization 头，
只有 system prompt、模型回答和一次 SQL 的返回值。

## 8. 附：原始数据是怎么取回来的（这一段跟模型无关）

放在这里是因为**它是"两处承诺对不上"的真实案例**，值得留档。

上一版 README 的「30 秒上手」第一步是 `python tools/build_truth_db.py`，
而那个脚本只会找本地文件、不会下载 —— 新 clone 的人第一步必然失败。
补上取数之后，又冒出一个新问题：**换了数据通路，原来的结论还成立吗？**
下面是实测，不是推断。

### 8.1 UCI 现在给的是什么（实测）

```
$ curl -sI "https://archive.ics.uci.edu/static/public/352/online+retail.zip"   # 200
$ python tools/build_truth_db.py --download
    复用已下载的 online+retail.zip（23.7 MB）
    已解出 data/raw/Online Retail.xlsx（23.7 MB）
    已写出 data/raw/online_retail.csv（541,909 行，48.5 MB）
```

| 事实 | 值 |
|---|---|
| zip 大小 / 内容 | 23,715,478 字节 / **只有一个 `Online Retail.xlsx`**（没有 CSV） |
| xlsx 大小 | 23,715,344 字节 |
| `xl/worksheets/sheet1.xml` 解压后 | **184,640,367 字节**（所以必须增量解析） |
| `xl/sharedStrings.xml` | 9231 条唯一字符串 |
| 首次下载耗时 | 约 135 秒（146 秒那次是网络抖动） |

`Online Retail.xlsx` 里的老 CSV **已经不在** UCI 的下载页面上了 ——
所以"零依赖解析 xlsx"不是可选优化，是必须做的事。

### 8.2 两个只有真跑过才会发现的单元格细节

```xml
<!-- 第 2 行原文 -->
<c r="A2" s="5"><v>536365</v></c>          <!-- InvoiceNo：整数 -->
<c r="D2"><v>6</v></c>                     <!-- Quantity：整数 -->
<c r="E2" s="7"><v>40513.351388888892</v></c>   <!-- InvoiceDate：Excel 序列号 -->
<c r="F2"><v>2.5499999999999998</v></c>    <!-- UnitPrice：**不是 2.55** -->
<c r="G2" s="8"><v>17850</v></c>           <!-- CustomerID：整数 -->
```

- **`InvoiceDate` 是序列号，不是日期字符串**：`40513.351388888892` → `2010-12-01 08:26`
  （原 CSV 写作 `12/1/10 8:26`）。当成普通数字读下去，所有按月分组的结论会整体偏移。
- **`UnitPrice` 存的是 `2.5499999999999998`**，而不是人写的 `2.55`。
  这解释了一条设计纪律：**转换时一律原样透传、不做任何格式化** ——
  任何"顺手美化一下"的动作都可能让 `Amount` 的乘积漂移，
  而漂移是**逐行累积**的，最终体现在总销售额上。

### 8.3 逐行等价验证：换通路之后结论没变

这是这一节最重要的一条。做法是**两份源各建一次库，然后逐行比对**：

```bash
# ① 老通路：本机那份 ISO-8859-1 的原始 CSV（43,954,909 字节）
python tools/build_truth_db.py --src "<老 CSV>" --out .tmp/legacy.db

# ② 新通路：已经由 xlsx 转出来的 CSV（即 data/truth/retail_truth.db）
# ③ 两份库都按同一组列排序后逐行比对
```

| 比对项 | 结果 |
|---|---|
| 行数 | 392,692 vs 392,692 |
| **逐行完全相同的行数** | **392,692** |
| 有差异的行数 | **0** |
| 编码判定 | 老 CSV → `ISO-8859-1`；新 CSV → `utf-8`（两种都判对了） |
| 7 项口径自检 | 两条通路**各自全过** |

顺带也验证了 `sniff_encoding()`：它对同一份数据的两种编码给出了两个不同的正确答案，
而不是"都当 UTF-8 解"（那样会静默乱码）或"都当 latin-1 解"（那样会更糟）。

### 8.4 这条验证链的边界

- 逐行等价只能证明**这两份输入等价**，不能证明 UCI 给的 xlsx 与 2011 年的原始发布
  完全一致。能做的最强验证就是 392,692 行这个闸门。
- 日期只到**秒**。原 CSV 本身只有分钟精度，所以"秒"这一级是与 xlsx 对齐后新出现的
  信息；`40513.351388888892` 的小数部分乘 86400 得 30360.000000027 秒，四舍五入到 30360
  ——**不是**靠截断，是靠四舍五入。
